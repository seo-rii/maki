# Maki development guide

Maki is a crash-consistent, bounded, privilege-separated encrypted block-storage
layer exposed through nbdkit. `SPEC.md` is normative. Start with
`docs/architecture.md`, `docs/configuration.md`, `docs/operations.md`, and
`docs/testing.md` for maintained project documentation. `docs/status.md` is
the only page that states current support; dated campaign reports live under
`docs/qualification/` and never claim current state. Run
`python3 -B scripts/check_docs_links.py` after moving or renaming a document
or a heading (it also verifies anchors).

## Ground rules

- **TDD is mandatory** (SPEC §41): failing tests land before implementation; bug fixes start with a reproducing regression test. Extended gates live as `#[ignore]`d tests; their historical `phase*_gate_full` names remain stable test identifiers.
- **Durability invariants are non-negotiable** (SPEC §12): plaintext never persisted; FLUSH/FUA-acknowledged data survives any crash; `checkpoint_sequence ≤ durable_sequence`; corrupted ciphertext ⇒ EIO, never data; allocated-but-invalid slots ⇒ EIO, never zeros.
- **Secrets**: plaintext and keys travel in `SecretBuffer` (zeroize-on-drop, no `Clone`, redacted Debug). Never log payloads; never put literals in configs (SPEC §9). `maki-privileged` must never gain a dependency on any crypto crate (PRIV-010 by construction).
- **Providers are untrusted**: results go through `CheckedProvider`/validators; unprovable capabilities are `Absent` (SPEC §16).

## Commands

```bash
cargo test --workspace --locked
cargo test --workspace --release --locked -- --ignored
cargo test -p maki-core --locked --test phase3 -- --nocapture
```

The Unix-only suites (control socket, `statvfs`; `cfg(unix)`) and the
Linux-only ones (privileged executor, process hardening;
`target_os = "linux"`) are skipped on Windows; run them on Linux (CI, or WSL
from this machine) before claiming a change is verified. `review_*.rs` test files are
the regression suites for the 2026-09-02 external review; their scope and the
status of every finding live in `docs/review-remediation.md`.

Failpoint-using tests must hold `failpoints::test_lock()` (failpoints are process-global). Timing-sensitive async code uses the injectable `Clock` (`ManualClock` in tests) — never real sleeps.

## Traps that already bit us (don't re-learn)

- crc32 of a self-checksummed image is a constant; golden vectors hash the payload excluding the trailing CRC ([architecture](docs/architecture.md)).
- Checkpointing the newest overlay version can lose a unit whose newest write is volatile; keep latest and latest-durable versions separately ([architecture](docs/architecture.md)).
- A dying WebSocket connection must only fail requests from its own generation ([architecture](docs/architecture.md)).
- WAL-style replay needs a flushed header or salt to gate epochs ([testing](docs/testing.md)).
- On-disk format changes require a format-version bump + new golden vectors; `tests/golden/*.crc` failing means you broke compatibility.
- An automatic journal roll advances `durable_sequence` *inside* `append`; always promote the overlay before publishing a newer version of the same unit, or a checkpoint can delete the only copy of a durable write ([remediation log](docs/review-remediation.md), M-002).
- Clear a persistence dirty flag only after the directory fsync that makes the new file durable; clearing earlier lets a retry skip the step (M-003).
- Unsynced journal records persist in any order: a valid record after damaged bytes does not prove the damage is durable. Classify with the durable mark, never by what follows (M-007). The mark is a plain write and is often lost in the crash itself; with no mark for the final segment only its header is proven, so everything beyond is a torn tail (S-04). Recovery must leave the final segment ending exactly at its last record: a surviving zero tail becomes "corruption" once the segment is sealed as non-final (S-05). Crash tests must use `CrashableBacking::with_tearing`, which tears *any* unsynced write.
- An A/B record falling back to its older generation is *normal* (torn write, later damage), and the older allocation map / shard catalog does not list the newest slots or shard. Slot headers are authoritative: probe them instead of reading "bit 0" as zeros ([remediation log](docs/review-remediation.md), S-01).
- Debug builds run `check_invariants()` on the overlay, journal, and volume after every mutation; a sanitizer panic in a test is a real accounting bug, not a flaky test. Keep the checks O(1)-ish on large structures (they sample).
- Journal segment indexes are never reused: the durable mark outlives the segment it names, so numbering continues above the mark even when a checkpoint has deleted every segment (S-03). Run the release gates (`-- --ignored`) after touching recovery; the default suite did not catch this.
- A process restart is not a power loss: recovery reads back page-cache bytes that were never fdatasync'd. Everything recovery accepts must be fsync'd before the writer resumes, or a later FLUSH acknowledges data the next power loss removes (K-01). That includes the superblock: a create that failed or died after writing `superblock.a` leaves a readable, possibly volatile copy that a retried create refuses to replace, so `recover` rewrites both copies from their exact bytes (selected first) and completes a missing one before any other repair. `CrashableBacking` models this: `drop` + `recover` is a restart, only `crash*` drops pending writes, and `crash*` also kills every handle and lock opened before it (their operations fail with an I/O error) and every process view started before it: start the code under test on `backing.process()`, never on the test's own backing, or a volume, engine or worker left alive across a crash keeps creating and syncing files no dead process could.
- An A/B side that passes its CRC but does not decode as the record type is *invalid*, not "newest": choose the side to overwrite from the typed view (O-10).
- Anything an HTTP endpoint can steer must not re-send plaintext: redirects are refused, never followed (C-01).
- A failed `fdatasync` is never retried by calling it again: Linux marks the dirty pages clean and the retry "succeeds" without writing them. The journal fingerprints the records accepted since the last sync, re-reads and rewrites them in bounded chunks, verifies the fingerprint and only then syncs (changed or lost bytes refuse the barrier); recovery rewrites and verifies every accepted segment prefix before syncing it (F01 / BUG-021). `CrashableBacking` models this by default: a failed sync keeps its dirty writes readable but uncertain (a later crash may or may not keep them, `crash_all_lost` drops them), a bare retry writes nothing, and a successful sync writes back every re-dirtied 4 KiB page whole, so a later write that shares a page with failed bytes makes them durable — a test proving the rewrite is required must leave a failed page untouched by later writes.
- `write_at` can persist a prefix and then fail: the file is then longer than the writer's logical end, and sealing it makes that tail "corruption". Truncate back to the logical end before appending or sealing, and keep the cleanup flag until that truncation is synced; the debug sanitizer checks the file length (F03 / BUG-020).
- `mlock`/`munlock` work on whole pages with no reference count: `SecretBuffer` counts owners per page under one lock, and only the last owner unlocks, after zeroization (F04 / BUG-006).
- State derived from plaintext is plaintext: a search table over a unit (a KMP failure table reproduces a two-valued unit exactly) must not sit in ordinary heap memory, where it is not page-locked and is freed unerased. The plaintext echo check uses two-way matching, which keeps only a few positions on the stack (AUD-100, `review_plaintext_scan_memory.rs`).
- A `flock` lock belongs to the open file description, and every child forked by any thread (each `Command::spawn`, between its fork and its `exec`) holds a copy of it, close-on-exec descriptors included. Closing the holder's descriptor then leaves the lock held for that child, and an immediate reattach fails with `AlreadyAttached`. Every lock guard unlocks before it closes (`review_lock_release.rs`); do not serialize tests around process spawns instead.
- A polled `flock` loses its turn: Linux serves blocked requests in order (observed, not specified by POSIX), but nothing hands the lock over at release; the first waiter is woken and must take the lock itself. A non-blocking attempt wins only if it lands between a release and that waiter taking the lock, which a loop that sleeps between attempts (the hook's 50 ms) practically never does, so every helper that queues meanwhile overtakes it. A bounded wait makes a blocking request on a thread of its own and abandons it at the deadline; a lock granted later is released with the dropped channel (AUD-143, `TrustedState::lock_until`).
- A root process creates entries below a `FileBacking` root for the owner of the directory it creates them in, or a root-run check leaves files the daemon cannot open. Give away only an entry this process has just created, before it is linked or holds a byte, never one that already exists, and never publish a file another user may hold open: a leftover `anchor.next` (AUD-111) or `rollback.format.next` (AUD-186) is removed, not written into. A root-run creation killed between creating a file under its name and giving it away leaves a root-owned file the daemon user may not open: under the local staged marker's name it is removed like any leftover, never refused for that, and an arena or manifest slot is refused with the way out (AUD-186).
- A single-copy record that nothing else can tell from damage (the rollback format marker, the remote enrollment binding, the witness anchor, the remote witness state, and the first superblock copy of a new volume, which has no other side yet) is never created under its final name and filled afterwards: a kill, a failed write or a power loss leaves an empty or torn file that neither creation nor recovery can tell from a damaged one. Write and sync it under a temporary name (`rollback.format.next`, `remote.enrollment.next`, `anchor.next`, `remote.next`, `superblock.next`), rename it and sync the directory. The staged file is never read: the next attempt replaces it, writing it again from the start or, for the anchor and the format marker, removing it and creating a new one (AUD-111, AUD-186). Files whose interrupted creation recovery tells apart by design, such as journal segments (the durable proof and mark), A/B sides and sparse shard data files, follow their own rules (AUD-114, AUD-115, AUD-136, AUD-139).
- "No valid superblock" alone never means "never used": it is also what a used volume whose superblock copies are both damaged looks like. A plain root with a superblock file that holds none is refused by `create` and never initialized again. A local rollback creation that stopped after its witness anchor is continued by `create` only on evidence damage cannot produce and a used volume cannot have: the pair opens against its witness (the manifest and every committed page are then authenticated) and holds no superblock copy and nothing but what a creation writes before its superblock (`maki_format::init::unfinished_creation`, which goes by the entries that exist, not by whether a copy decodes). A pair that does not open keeps the enrollment's refusal; `review_interrupted_volume_create.rs` cuts the whole command in the crash model.
- Files that are published one after another in a directory need the earlier *name* durable before the later file is staged. Rewriting and fdatasyncing a file that recovery accepted makes its bytes durable, not its directory entry, and a power loss keeps entries in any order: enrollment recovery staged the binding over a marker whose rename was still volatile, and left a binding without a marker that neither command continued. `republish_root` syncs the directory first, also when a staged binding is already there. `volume create` still continues such a root from an earlier release: the staged binding is never read, and a published one is accepted only if it is the binding this creation would write, under a released authority that was never activated; its bytes are synced again before the marker's directory sync makes its name durable, and for the same reason recovery does not sync the directory while a binding it found is still unsynced. A snapshot destination accepts neither. A staged name is accepted only for what the command can write again, a regular file with one name: a link, a directory, a FIFO or a second name under it is refused before anything is published (unrefused, a link or a directory there failed the command after its marker and at every later run; a FIFO or a second name was removed by the failed run) (`review_binding_without_marker.rs`).
- The rewrite rule applies to A/B records too: before the stale side is overwritten, the preserved (typed-valid) side's exact bytes are rewritten and synced (file and directory), so the durable copy is safe before the target is touched. A failed sync of the target is *not* emptied — the preserve step already protected the durable copy, and a readable newer generation is kept for a later store to preserve in turn. This BUG-001 preserve-first rule subsumes the earlier N-09 empty-on-failure approach; do not re-add the emptying (it discards a newer generation and the two designs' tests contradict each other).
- An A/B side that does not decode is not just "about to be overwritten": it can hold all but a few sectors of an earlier cut store, written with the generation the next store will use too. Overwriting it in place and being cut again can complete the *earlier* record (the missing sectors are the ones both share), and `load` then selects an attempt that recoveries in between had fallen back from. `AbStore::store` truncates such a side to zero and syncs that before writing (one extra fdatasync, only for an existing undecodable target; the truncation is repeated on every retry, because one whose sync failed is not known to be durable). This does not touch a decodable side: the preserve-first rule above stands (`review_ab_torn_reuse.rs`).
- A circuit-breaker probe must return its half-open slot on every exit, verdict or not: the dispatcher holds a `BreakerPermit` whose drop releases the slot, so a deadline or a cancelled future never wedges the circuit (N-10 / BUG-004).
- Recovery must make the checkpoint state it selects durable *before* the writer resumes: a restart can hand it a page-cache-only newer checkpoint, and reclaiming journal against it then losing power leaves an older checkpoint whose covering segment is gone ("does not bridge"). `recover` re-stores the selected state and fails closed if that store fails; the store's preserve-first step (BUG-001, above) keeps the other valid copy durable, and a failed target sync is not emptied (BUG-022).
- `grow` is not exempt from attach identity: it takes the attach lock and must match the trusted record (targets and live NBD backend identity) before any `lvextend`/`xfs_growfs`, exactly like detach — its plan carries the `AttachmentIdentity` (BUG-018).
- LVM resolves a VG name over its own device scan, where another disk's VG can carry the same name, so every LVM command the helper runs takes `--devices`: the candidate devices for the preflight report, the verified ones for activation and its rollback, the recorded ones for detach, recovery and grow. Activation and the deactivations also select `vg_uuid=` where the VG UUID is known; `lvextend` has no `--select`. A `--select` that matches nothing (the PV cannot be read) exits 0 without doing anything, so the deactivation of a record with a mapping proof, or of one from before proofs and intents, also names the VG and fails instead, which keeps cleanup's fallback (it runs only after a nonzero exit) reachable, and the deactivation of an activation intent observes the mappings again instead of trusting its status. A device-mapper holder is attributable to a VG only by its uuid `LVM-<VG UUID><LV UUID>[-suffix]`; one without such a uuid is unknown, never another volume's (AUD-118, AUD-134, AUD-135).
- `NBD_CMD_CONNECT` answers `EBUSY` while anything holds the unconnected device open: opening `/dev/nbdN` allocates the device's configuration and keeps a reference to it, and udev probes a device on the change event of every disconnect, so a connect right after a disconnect of the same device (the allocator takes the lowest free index again) is refused while sysfs shows no `pid` and no `backend`. The converse holds too: those attributes go only when the last reference is dropped, so they outlive a successful `NBD_CMD_DISCONNECT` while anything that already held the device open at the disconnect (a probe of an earlier event, a monitoring tool, multipathd, an operator's `blkid`) still holds it. The disconnect's own change event is sent only when they go (`nbd_config_put`), so the probe it starts cannot keep them: that probe is what makes the next connect `EBUSY`. `nbd-disconnect`, detach and cleanup therefore share one wait for them (`exec::await_release`: every 100 ms for up to 15 s, never past the caller's `finish_by` deadline; another backend identifier means the disconnected connection is gone, an unreadable one fails), and detach and cleanup retire the record only when the device then shows no connection at all. They wait without the attach lock, or the cleanups of many volumes stopping together queued 15 s each on it and from about the eighth on reached `TimeoutStopSec=120` (AUD-205): an `exec::Turn` lets go of it before the wait's first sleep, so only when the first look after the disconnect still shows this connection (a first look showing none or another identifier keeps the lock and reads nothing again), and, unless the wait then ends with this connection still shown or unreadable (which fails without it), takes it again, in turn, before anything is acted on; under it the record must still be the one they disconnected (retired meanwhile is a success, replaced is kept and fails as replaced, also when the replacing attach took the same device and its new identifier is what ended the wait: "disconnect has not completed" would send the operator to a cleanup that tears that attachment down). Meanwhile only another helper of the same volume can replace or retire the record, and it sees what a kill during the wait leaves; for every other helper the record still reserves the device. The failed-start hook keeps the lock through its wait (`recover_tests.rs`, `the_failed_start_rollback_keeps_the_attach_lock_through_its_wait`; the rest is `review_release_wait_lock.rs`). A device that still shows this connection keeps the record and the refusal "disconnect has not completed", and a later run finishes once nothing holds the device open; one that shows another connection keeps it too, and a later cleanup retires it only by the displaced-record rules (`detach_and_cleanup_wait_for_a_backend_that_outlives_its_disconnect`, `acknowledged_but_incomplete_disconnect_preserves_cleanup_authority_for_retry`). Detach and cleanup wait on the `System`'s `Clock`, `nbd-disconnect` on the clock its caller passes (`RealClock` in production): a test whose backend can linger needs a manual clock, or it sleeps up to 15 s for real. A device that looks free is no promise: a connect retries `EBUSY` for up to 5 s from the first busy answer, within the step's deadline and only while the device still shows no connection. The kernel answers that `EBUSY` before it takes the socket, so the retry sends its request on the connection already negotiated (checked with a peek that consumes nothing) and negotiates again only when that one was closed or shut down: the plugin serves one connection, nbdkit closes one a moment after its peer did, and a handshake that arrives earlier is refused with `NBD_REP_ERR_UNKNOWN`. That refusal is a busy answer too, also for the first handshake after a disconnect. An opener shows nowhere in sysfs, so an allocated device that stays busy to the end is given up for the next free one, record first; a pinned one is not (AUD-150, `nbd_kernel::connect_retrying`, `retry_tests.rs`, `review_busy_allocated_device.rs`).
- A recorded device that shows no connection has no mount or mapping of it left: the kernel keeps a connection's `backend` and `pid` while anything holds the device open, a mounted filesystem or an LV mapping above all (read from its NBD driver; seen in CI on Linux 7.0 for the mapping, which XFS was mounted on and which alone kept them after the unmount), and a dead daemon's device keeps showing the connection until a disconnect. Cleanup's disconnected recovery therefore finds nothing to unmount or deactivate on Linux and only retires the record, and a test that must reach it disconnects the device and releases it by hand first, as the privileged runner's `--kill-daemon` does (`privileged_validation_nbd.py kernel-disconnect`, then `umount` and `dmsetup remove` while the connection still shows); both of CI's first kernel runs took the detach path (AUD-203). Cleanup logs the path it takes.
- A socket handed to the kernel keeps its socket options. The kernel's NBD receive loop reads with the socket's `SO_RCVTIMEO`, so a receive timeout left from the handshake kills an idle device's connection, and the kernel sets `SO_SNDTIMEO` only for `NBD_ATTR_TIMEOUT`, so a send timeout left from `connect(2)` fails any later send that waits that long for buffer space. Bound the handshake with `poll(2)` and per-call `MSG_DONTWAIT`, and clear a timeout used for the connect (AUD-149, `nbd_kernel`, `an_export_is_opened_on_a_blocking_close_on_exec_socket_without_timeouts`). The file's `O_NONBLOCK` does not reach the kernel's own I/O, which passes its own message flags; the helper keeps the socket blocking all the same.
- A clean `shutdown` must drain live control sessions, not just stop accepting: sessions run in a `JoinSet` that `serve_with_shutdown` aborts *and awaits*, or a lingering session keeps an `Engine` clone and the volume lock past a "successful" detach (BUG-015).
- A remote transport needs an overall per-RPC timeout, not only a connection timeout: a server that stalls after headers or before trailers otherwise pins its inflight slot forever. The gRPC provider wraps readiness + the unary call in one `tokio::time::timeout` (BUG-017).
- A TLS failure is an endpoint failure only where its typed rustls error reaches the transport, and it reaches further than the connection attempt: on an established connection tokio-rustls returns it inside an `io::Error`, whose `source()` skips the inner error, so walk each `io::Error`'s `get_ref()` too (the HTTP and WebSocket transports do), and never match text. The HTTP/2 library under tonic keeps only an I/O error's kind and text, so a TLS failure on an established gRPC connection stays a retryable status counted as sent (documented, `review_tls_failure_on_connection.rs` in each transport). A TLS failure of tonic's reconnect inside a cached channel does carry it: retire that channel even inside its initial progress window, or the next call goes through tonic's reconnect with its request queued and its failure counts as sent (`review_tls_unestablished_channel.rs`).
- Request-side JSON pointers must RFC 6901-unescape each token (`~1`→`/`, `~0`→`~`) to match the response side's `Value::pointer`, or a vendor field named `key/slot` is sent as `key~1slot` (BUG-024).
- Every shard-catalog commit publishes the *whole* in-memory catalog, including shards adopted at open (orphan data files). An adopted shard's allocation map must be stored and dir-synced before *any* commit, not only the one in `persist_allocations`; and a map an adopted shard loaded after a plain restart may exist only in the page cache (K-01), so it is re-stored, never trusted as durable (K-03 residuals, `review_r3b_durability.rs`). The randomized sweep there (workload → power loss or restart → oracle, with random sync failures) is the fastest way to shake out ordering bugs of this kind.
- On a cleared allocation bit, only a slot with no written byte is "unwritten": a hole is never partly written, so an undecodable non-zero header on a cleared slot is damage ⇒ EIO, never zeros (S-01 residual), and so is an all-zero header over ciphertext bytes that are not all zero: a header sector can read back as zeros while the ciphertext under it survives, and a header-only probe served a checkpointed unit as zeros (`review_zeroed_slot_header.rs`). The probe reads the header and the ciphertext area (64 + `max_ciphertext_size` bytes), never the alignment padding; the open-time audit, which only marks valid headers, still reads 64 bytes. The one crash state with a zero header over ciphertext is a torn first slot write, whose record is newer than the checkpoint (recoverable); a punched slot is answered by its discard bit first. A shard data file is created at its full sparse size and synced before use, so a file shorter than `units_per_shard × slot_size` is *truncated*, and a slot beyond its end is damage too, not a hole. That evidence is volatile: the next slot write past the end grows the file with zeros and the removed slots become "holes", so `open` marks them allocated (EIO until rewritten) and the marks are persisted before the file is grown back. The one legitimate short file belongs to a shard never written into (uncataloged, empty allocation map, no non-zero byte of a slot's header or ciphertext area below the end of the file, which only a slot write leaves and which cannot fall back as the catalog and the map can; a stale empty copy from an earlier creation attempt is *not* proof of use): its holes stay holes, and its size is set and synced again before the shard is written to or cataloged, because after a failed sync and a restart the page cache shows a full size the disk does not have (K-01 again). Shards are found by their allocation maps too: a map that lists a slot without a data file refuses attach (AUD-181). Damaging the newest map copy *and* the slot header together is exactly what media damage after a crash looks like; the media-damage sweep in `review_r3b_durability.rs` finds this class in seconds.
- A remote provider that declares context binding must receive the whole context on the wire (volume UUID, compatibility id, format version); the self-test probes each field, and a transport or config that omits one fails attach with a "decrypts to the original plaintext" probe error (R3-006).
- An `EndpointSet` reports the *intersection* of its endpoints' capabilities, quarantined ones included; never one endpoint's own contract (R3-004). What it reports must also be what it serves: a set bound to one plaintext size (`with_plaintext_size`, as the daemon's is) lists that size alone out of the common ones, because the batch scheduler admits by the reported sizes and the set refuses a whole coalesced call for one unit of another size.
- Attach probes a set's endpoints at once (`EndpointProbe`); probed one after another, three WebSocket endpoints that never answered held a healthy fourth past `TimeoutStartSec=180` at the default timeout. Their key canary checks still take turns in configuration order: the check loads, rewrites and on a new volume establishes the canary, an A/B record two stores must never write together, and the first endpoint in that order whose check succeeds must establish it, as before. A check that fails with a transport failure keeps the turn through the endpoint's remaining attempts, so endpoints that pass their self-test and fail their canary check still delay the ones after them one after another. An endpoint whose probe refuses the attach never ends its turn, so no endpoint after it reaches the volume, and the results are taken in configuration order. Each request of the probes and of the cross-endpoint check that ends reports progress, which the native plugin sends as `EXTEND_TIMEOUT_USEC`; only those views report (`ReportingEndpoint`), never a provider handed to the `EndpointSet` (`endpoint_probe_tests.rs`, `review_endpoint_probes.rs`).
- Per-crate builds on Windows cover the cross-platform code; the Linux-only suites (`review_abi.rs`, `review_secret.rs` smaps check, the control backlog test, the backing symlink test) need WSL, where `nbdkit-plugin-dev` is installed for the ABI probe.
- libtest captures a passing test's output and shows it only with `--show-output` or `--nocapture`, so a test that prints a skip notice and returns is a pass nobody sees. Where an environment is required, a missing precondition must fail: `scripts/run_root_tests.py` fails a test that still says it needs root when it ran as root (and lists every other skip notice), and `MAKI_TEST_REQUIRE_OTHER_FILESYSTEM=1` (set in CI) makes the rollback fixtures panic without a second filesystem (AUD-129, AUD-145).
- A GitHub container job runs its steps as root, but the workspace, `RUNNER_TEMP` and `HOME` (`/github/home`) belong to the runner's uid 1001. Root's `git` refuses the checkout ("dubious ownership"; `actions/checkout` trusts it only in a temporary git configuration), so a `git log` for `SOURCE_DATE_EPOCH` comes out empty, and fixtures that require root-owned ancestors closed to others (`regression_mount_target.rs`) refuse the workspace, `HOME` and `/tmp`. The `rhel9` job adds the workspace to root's `safe.directory` and exports a root-owned `0755` `TMPDIR` below `/var/lib`. A local chroot replay of such a job proves nothing about this unless it reproduces that ownership (a uid-1001 workspace and `HOME`, root steps): the first replay passed where CI failed (AUD-156). A container job's step without `shell:` also runs under `sh -e`, not bash: dash in `debian:12` refuses `set -o pipefail`, while CentOS Stream 9's `sh` is bash, so set `defaults: run: shell: bash` and replay each block under the shell the job will use (the first release run failed so).
- On EL9 install `nbdkit-server`, never the `nbdkit` metapackage: on a host with the targeted policy it pulls in `nbdkit-selinux`, whose `nbdkit_exec_t` label on `/usr/sbin/nbdkit` the policy lets systemd's `init_t` neither execute it nor use it as an entry point into `nbdkit_t`, so `maki@` would not start under enforcing SELinux (read from the policy, not observed). The RPM requires `nbdkit-server` and declares `Conflicts: nbdkit-selinux, nbdkit`, and the `rhel9` job installs `nbdkit-server`, with `nbdkit-basic-plugins` for the tests' exports (AUD-154, `test_package_conflicts_with_the_nbdkit_selinux_module`).
- rpm cannot stop a transaction from a scriptlet: a failing `%preun` keeps that one package and rpm goes on. Under an attachment `dnf remove maki` kept Maki and erased `nbdkit-server`, `lvm2`, `xfsprogs` and `kmod` as unused dependencies, and `dnf --allowerasing` installed a conflicting package beside it; `rpm -e maki` never showed it. The RPM names itself in `/etc/dnf/protected.d/maki.conf`, so dnf refuses such a transaction before it changes anything, and is removed with `rpm -e`. A protected package's `Conflicts` must name whatever brings the conflicting package in: with only `nbdkit-selinux` refused, `dnf install --allowerasing nbdkit` proposed to replace `selinux-policy-targeted` instead. Test package removal with the package manager operators use (`test_dnf_is_told_not_to_remove_the_package`, the `rhel9` job's `dnf remove` under a record).
- nbdkit asserts, rather than checks, that a request's FAST_ZERO flag was advertised (`backend_zero`: `c->can_fast_zero == 1`), so with `can_fast_zero` 0 one WRITE_ZEROES request with that flag, from any client of the socket, aborts a server built with assertions before the plugin can refuse it. Keep `can_fast_zero` at 1 and refuse the request in `zero_v2` with ENOTSUP, which the NBD protocol allows; before changing what any capability callback answers, compare nbdkit's `validate_request` with the assertions of `backend.c` (AUD-160, `review_fast_zero.rs`).
- CI runs Clippy with `-D warnings` on the baseline toolchain (1.94.0) and on the latest stable, and each refuses what the other accepts: 1.94.0 reports `clippy::nonminimal_bool` for `!x.is_some_and(..)`, which newer ones do not, and 1.100.0 deprecates `fetch_update` for `try_update`, which is not stable on 1.94.0. Run both before pushing and write what builds on both (AUD-179).
- CI runs the suites as an unprivileged user on a clean host and then the root-only step. A test that passes here as root, or because an earlier run left something behind (`/run/maki-attach`, which `verify` never creates), proves nothing about CI: replay a privilege-dependent test as an unprivileged user with an empty `/run`, which a private mount namespace gives (AUD-179).
- `fuzz/` is a Cargo workspace of its own whose `Cargo.lock` is not committed: the root's `[patch.crates-io]` does not reach it, and it fuzzed the crates.io `serde_json` and `bytes` rather than the vendored copies production builds. `fuzz/Cargo.toml` repeats the patch of every patched crate its graph uses, and the `fuzz` job starts `fuzz/Cargo.lock` from the workspace's (`test_ci_gate_validation.py`).
- A test of an ordering rule ("X is durable before the record is accepted") must run nothing between the acknowledged write and the crash that also does X, a checkpoint above all: #394's first catalog test had one and, like the whole maki-core suite, also passed when the catalog was stored only by that checkpoint, after the record (AUD-181).
- A test that depends on connect timing reaches a loopback listener by its IP literal, not `localhost`: Windows resolves `localhost` to `::1` first and a refused connect there takes about 2 s. Every remote transport starts the other address family 300 ms after the first attempt (the WebSocket and gRPC ones sooner only with less than 600 ms left or a `timeout` under 600 ms; an HTTP `timeout` under 600 ms gets a configuration warning), so `localhost` still costs about 300 ms there, which a timing assertion or a timeout that short does not survive (AUD-193). A test of the WebSocket connect across several addresses substitutes the provider's resolver and dialer (`connect_address_tests.rs`) instead of depending on the host's resolver; an HTTP one resolves the name through reqwest's override (`HttpCryptoProvider::with_client`, `connect_tests.rs`), a gRPC one through the connector's test resolver (`GrpcCryptoProvider::build_resolving`, `TestResolver`), and on Linux a loopback listener whose accept queue is full is an address that never answers; as root, a packet filter in a thread's private network namespace is a route that drops packets. A test of the other family needs the IPv6 loopback address, which some hosts (containers) lack: it skips without one unless `MAKI_TEST_REQUIRE_IPV6=1`, which CI sets. Under paused time, poll such a test's loopback I/O in a loop that yields (`without_advancing`, `run_for`): a runtime left idle advances the clock past the deadline while a real socket is still connecting.
- A port freed by dropping a listener is free for the next bind: a test that binds `127.0.0.1:0` beside another in the same process can be handed it, and its peer then serves what the other test meant to be refused. CI failed two tests of maki-crypto-websocket's `review_unsent_failover.rs` on that race (a dropped listener's port came back 44 times in 480,000 binds on Linux 6.18). Hold a socket that is bound and never listens for the test's whole life (`ClosedPort`, `the_refused_endpoint_keeps_its_port_while_a_test_uses_it`): Linux refuses a connect to it, while macOS drops the SYN (XNU's `tcp_input.c`, read, not run), so there such an endpoint goes unanswered rather than refused (AUD-225).
- A test that a call waits for a condition to end must show that the call returned after it ended, not only that the call succeeded and the condition is over by the next check: the first version of #406's kernel job also passed a detach that returned at once, as the review showed with a helper that did, because its opener let go of the device on its own two seconds later, before the release check looked. The runner now requires the opener's flushed "closing" line to be in its file when the detach returns (AUD-203).
- A fuzz oracle that skips inputs must decide as the code under test reads them, not by their bytes: #408's JSON oracles skipped serde_json's private raw-value key by its text, so the same key with an escaped `$` (`\u0024serde_json::private::RawValue`), which `Value` decodes to it, failed two targets on serde_json's own reading. They now walk the document with serde_json's deserializer, and unit tests hold the classifier, since one that skips every document still passes the seed replay (AUD-204).
- libFuzzer reads at most `-max_len` bytes of a seed and never generates a longer input (without `-max_len` it takes the longest seed's length, from 4096 bytes up to 1 MiB), and a run keeps a longer input only when it reaches new code. A bound a reader checks beyond 4096 bytes needs the target's length in `scripts/fuzz_campaign.py`, which the `fuzz` job and the qualification read (`test_fuzz_qualification_validation.py` checks each length against the bound in the Rust source and every seed against its length), and a seed that crosses it. The `fuzz` job passed `-max_len=4096` to `nbd_netlink` and so cut its 16,392-byte seed of a datagram beyond the buffer.
- A fuzz entry function must start no thread per input and free every heap block it allocates before it returns. libFuzzer runs every input of a run in one process, and under AddressSanitizer the process's memory grows with every thread it has started, ended or not (200 to 250 bytes an execution, measured on `nbd_handshake`'s server thread; without a sanitizer its RSS stayed flat): all eight processes of `nbd_handshake`'s qualification (two shards of 12 CPU-hours) ran out at `-rss_limit_mb=2048` after about 10 million executions each, the empty input among those libFuzzer wrote as out-of-memory. A server thread kept across inputs is no way out: libFuzzer counts each call's mallocs and frees in every thread, runs a call with more mallocs than frees again and, when that run ends so too, leak-checks the process, and stops checking per input after 1,000 such checks (`FuzzerLoop.cpp`); the kept thread freed each input's memory after the call had returned. `nbd_handshake` now puts the whole input into its socket before the client runs and reads the request after the client has closed. `review_fuzz_entry_threads.rs` counts each call's threads (the test binary's own `pthread_create`) and heap blocks (a counting global allocator).
- An exit status is not the evidence: libFuzzer's `-merge=1` exits 0 after an input failed its inner process. The inner process writes the input to `-artifact_prefix` (`crash-`, `timeout-` or `oom-`), the outer one starts it again (`MERGE-OUTER: attempt 2` in its log), which leaves the input out, and the coverage run of the merged corpus then passes too, so `fuzz_campaign.py merge` reads the merge's artifacts and counts its attempts. Likewise a fault a validation injects must prove that it fired: `documented_quickstart.py --stop-once` took any failed first run for the stop at its shim until the shim left a mark the program requires (`test_fuzz_qualification_validation.py`, `test_documented_quickstart_validation.py`).
- `actions/upload-artifact@v4` fails with "Maximum call stack size exceeded" on a directory of more than about 123,000 entries (`@actions/glob` spreads each directory's entries into one call; measured on Node 22, while the action declares `node20`, where the limit was not measured): the qualification lost every shard corpus of four targets (143,835 to 405,750 files), and nothing in the summary told a merge of their seeds alone from a real one. Upload a large directory as one `tar`, named only once `tar` succeeded, and make the consumer check what it received against what was planned and what the producer counted (`fuzz_campaign.py merge --planned-shards`, the summary's corpus counts, `test_fuzz_qualification_validation.py`).
- A test or tool that reads a tracked text file must not assume LF line ends: `.gitattributes` sets `* text=auto`, so a Windows checkout (CI's Windows jobs) normally has CRLF in every text file not marked `-text`. The first version of #401's seed replay split `fuzz/Cargo.toml` on `"\n["` and found no target there (AUD-200). Read lines with `str::lines` and trim them, or mark an input compared byte for byte `-text`, as `fuzz/seeds/**` is.
- `kill -0` is no liveness test for a process that sudo started: sudo checks its policy with real, effective and saved uid 0 (sudoers' `PERM_ROOT`), so for that moment the invoking user's `kill -0` on its PID fails with EPERM although it runs. The privileged runner's wait for its opener stopped so at its first look in the Debian 12 guest (the EL9 guest's run passed, though sudo 1.9.5p2 there does the same). Read `/proc/PID/stat` instead, a zombie counting as gone (`process_running`, `test_the_wait_does_not_signal_the_opener_that_sudo_started`).
- A merge that resolves a conflict by replacing a block can drop a test beside it, and the suite still passes: #413's merge of #410 rewrote the two cleanup dispatch tests and lost `acknowledged_but_incomplete_disconnect_preserves_cleanup_authority_for_retry`, which both parents had and the NBD trap above cites. After a conflicted merge, compare every test name, by file, with both parents and their base: each occurs as often as in ours plus theirs less the base (AUD-208).
- GitHub's runner ends a step (its time limit, a cancelled run) by signalling only the step's own process: SIGINT, SIGTERM 7.5 s later, a kill 2.5 s after that. That process is bash running the step's script, which does not pass a signal on to the command it waits for, so a step whose child must record what it did when interrupted `exec`s it: #415's first fuzz qualification lost an interrupted shard's record, and its test had signalled the Python process directly. `StepCancellation` (`test_fuzz_qualification_validation.py`) replays the sequence on the steps' own scripts (AUD-210).
- `systemctl stop` of a target returns once the target's own job is done, before the units it is ordered after have stopped, and systemd garbage-collects a unit once it is inactive, after which `systemctl show` loads a fresh one whose timestamps are 0. Wait for each unit itself, and read when its stop began and ended from PID 1's journal (`journalctl --boot --output=json _PID=1 UNIT=<unit>`, the stop job's begun and finished messages with one `JOB_ID`), as `scripts/stop-together-validation.py` does; its first three CI runs failed on these two (AUD-208).

## External qualification

Kernel NBD/filesystem checks, OS-enforced privilege checks, vendor endpoint
qualification, real databases, and disruptive power-loss testing require
dedicated Linux or hardware environments. Follow `docs/testing.md`; operational
commands and safety boundaries are in `docs/operations.md`.
